# T3 Code server

T3 Code is a WebSocket server that hosts agent sessions for web, desktop, and mobile clients. It runs as a user service on the host named by `tools/t3/deployment.json` — systemd on Linux, launchd on macOS (the T3 installer picks).

This repository tracks the deployment declaration and desired configuration only. The service unit, `~/.t3/` runtime state (database, secrets, tokens, pinned versions), and Tailscale state are generated or live data and stay untracked.

## Prerequisites

`t3ctl.py` is stdlib-only Python. The host needs a user service manager (`systemctl --user` on Linux, `launchctl` on macOS), a JavaScript package runner (`npx` or `bunx`), and `tailscale` when tailnet exposure is enabled. The runner only fetches the `t3` CLI: the service itself runs a self-contained release archive pinned under `~/.t3/runtime/versions/<version>/t3`, so the host needs no Node for the server.

## Operate

All operations go through `tools/t3/t3ctl.py`, which reads `deployment.json` for the declared host and channel, and refuses to mutate on any other host:

| Command | What it does |
| --- | --- |
| `python3 tools/t3/t3ctl.py install` | Bootstrap the service on the declared host, refresh the harness packages, apply desired settings, report next steps |
| `... t3ctl.py status` | Declared vs. live state: host match, unit, version, port, endpoint probe, exposures |
| `... t3ctl.py doctor` | `status` plus unit file, service state, and recent logs |
| `... t3ctl.py restart` | Restart and wait for the endpoint to answer |
| `... t3ctl.py update` | Run `t3 service install` from the channel head: moves the service, launcher, and pinned runtime to the newest release, or repairs them; then refreshes the harness packages and runs `apply-settings`. Required when a client reports that a release needs a newer service launcher — in-app updates cannot replace the launcher |
| `... t3ctl.py apply-settings` | Merge `server-settings.json` into live settings while stopped, point each harness driver's `binaryPath` at its cached executable (see [Providers](#providers)), then restart |
| `... t3ctl.py pair` | Mint a tailnet pairing link; also reconciles `tailscale serve` on `exposure.tailscaleServePort` to the live port |
| `... t3ctl.py connect …` | T3 Connect management (`login`, `link`, `publish`, `status`, `unlink`) |
| `... t3ctl.py logs [-n N]` | Recent service journal and boot log |

First-time Connect setup on a new host: `connect login` (interactive browser auth), `connect link`, `restart`. With `exposure.publishAgentActivity`, also `connect publish` + `restart`.

## Providers

Disabling a driver takes both `providerInstances.<id>.enabled` and the legacy `providers.<id>.enabled`: at load, T3 re-enables Cursor, Grok, and OpenCode for anyone whose thread history used them unless the legacy flag is saved explicitly (`apps/server/src/serverSettings.ts`, `restoreUsedProviders`).

`apply-settings` points each harness driver's `binaryPath` at its sync wrapper in `~/.local/bin` by absolute path, so T3 runs the harness through the SSOT like any other launch; the Claude driver spawns without a shell, so a bare name is not reliably resolved. The wrapper's `sync launch` startup counts against T3's 4 s Claude `--version` probe; if the Claude provider flaps between ready and error, fix the wrapper's startup time in sync rather than bypassing it.

Both harnesses read their synced homes and route through CLIProxyAPI, so no provider login is needed. Codex lists the gateway's catalog natively through `model/list`, so `customModels` stays empty. Commit messages, branch names, and thread titles use T3's default text-generation model unless `textGenerationModelSelection` is set.

## Reset to a clean slate

Removing projects in the UI or with `t3 project remove --force` only soft-deletes them: the history stays in `state.sqlite`, and the checkpoint refs stay in each repository. For a real reset, move the database aside. The server recreates it and runs all migrations on the next start. `environment-id` and `secrets/` hold the server and Connect identity, so Connect clients reconnect on their own. Direct and tailnet pairings live in the database, so re-run `pair` afterwards.

```sh
systemctl --user stop t3code.service
ls -A ~/.t3/runtime/db-backup          # must be empty: the launcher restores from here
cd ~/.t3/userdata
rm -f state.sqlite state.sqlite-wal state.sqlite-shm
rm -rf attachments/* logs/* browser-artifacts usage-*.json model-manifest.json ~/.t3/caches/*
rm -f secrets/dpop-proof-* secrets/cloud-*-jti-* secrets/cloud-*-nonce-*
echo '{}' > settings.json
# checkpoint refs T3 left in each repository it touched
for r in ~/repos/* ~/.config/agents; do [ -d "$r/.git" ] || continue; git -C "$r" for-each-ref --format='delete %(refname)' refs/t3 refs/t3code | git -C "$r" update-ref --stdin; done
python3 ~/.config/agents/tools/t3/t3ctl.py apply-settings
python3 ~/.config/agents/tools/t3/t3ctl.py pair
```

## Deploy on a new host

1. Update `server.hostname` in `tools/t3/deployment.json` and commit.
2. On the new host: `python3 tools/t3/t3ctl.py install`, then the Connect steps above if enabled.
3. On the old host: `t3 service uninstall` and `t3 connect unlink` via `t3ctl.py connect …`.
4. Re-pair clients; Connect environments reappear through the account link.

## Troubleshooting

### Threads stuck in `running`

A thread whose provider process died mid-turn (server restart, update, crash) can show as running forever. Do not repair `state.sqlite` by hand. Run `t3ctl.py restart`: every boot runs the `provider-sessions.reconcile` startup phase, which settles orphaned sessions and turns and tells the user to send a new message. With `continueThreadsAfterServerUpdate` on (as in `server-settings.json`), threads with a resumable provider cursor are instead resumed with "Continue where you left off." Without a restart, **Stop** in the web UI also recovers a dead session.

Source: `apps/server/src/serverRuntimeStartup.ts` (`reconcileProviderSessions`). If the boot log reports `provider session startup reconciliation failed`, read that function before touching the database.

## Deployment file

`tools/t3/deployment.json` fields:

| Field | Constraint | Meaning |
| --- | --- | --- |
| `server.hostname` | Local OS hostname | Host that runs the T3 Code service |
| `channel` | npm dist-tag | Release channel for install/update commands |
| `exposure.tailscaleServe` | Boolean | Server is proxied by `tailscale serve` on the tailnet |
| `exposure.tailscaleServePort` | Integer, optional | Tailnet HTTPS port for that proxy; upstream defaults to 443, which CLIProxyAPI's Funnel already holds on munich |
| `exposure.connect` | Boolean | Environment is linked to T3 Connect |
| `exposure.publishAgentActivity` | Boolean | Server pushes agent activity to linked mobile clients |

## Settings file

`tools/t3/server-settings.json` is merged into `~/.t3/userdata/settings.json` by `apply-settings` (or `install`/`update`). Tracked keys win on every apply; UI changes to untracked keys survive. Keep only non-secret, host-independent values; `~` expands to the server user's home. Sensitive or per-client changes belong in the client UI.

Validate every edit against `packages/contracts/src/settings.ts` before applying: one invalid value makes the server ignore the whole file and run on defaults (it logs `failed to parse settings.json`). The server also drops unknown keys and values equal to the defaults the next time it writes the file.

Not tracked, on purpose: `keybindings.json` (the server seeds and backfills defaults into it on every start, so a tracked copy would churn), appearance and composer preferences (client-side, stored per browser or device), and per-project overrides (keyed by project IDs that a reset regenerates). Worktree setup scripts would belong in `defaultProjectScripts`: the server runs those, and it only imports a repository's `t3.json` scripts through the UI.

The tracked settings assume an always-on host driven remotely: the background-activity profile uses the performance cadence with lock-pausing off, so a locked desktop session never stalls background work. On a battery-powered or locally used host, revisit that profile. `storageCleanup` removes a thread's worktree when its pull request merges or the thread is deleted (never a dirty worktree), and prunes rotated logs and browser artifacts after 14 days. Setting keys and defaults are defined in the vendored source under `packages/contracts/src/settings.ts` and `packages/shared/src/backgroundActivitySettings.ts`.
