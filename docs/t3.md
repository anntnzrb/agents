# Run T3 Code with Pi

T3 Code runs as a user service on hosts declared in `tools/t3/deployment.json`.
Each host has independent projects, threads, pairings, and runtime state. Add
another host only when you want another environment, not a replica of Munich.

## Install and pair a host

1. Add the host's short hostname to `tools/t3/deployment.json`.
2. Run sync on that host to install the Pi wrapper and maintenance timers.
3. Install the service:

```sh
uv run --script tools/t3/t3ctl.py install
uv run --script tools/t3/t3ctl.py apply-settings
uv run --script tools/t3/t3ctl.py pair
```

Open the pairing link on a device connected to the tailnet. Pairing credentials
expire, so rerun `pair` when needed. V2 servers require V2 clients. Use the
compatible mobile beta until the store release supports V2.

The deployment file owns release selection and exposure. `channel` accepts an
npm dist-tag or an exact version. An exact version disables unattended updates.
Tailscale Serve is tailnet-only. T3 Connect is separate and requires interactive
login, linking, and a restart when enabled.

## Providers

`tools/t3/server-settings.json` owns desired server settings. `apply-settings`
merges those settings while stopped, sets Pi's absolute binary path to the
installed sync wrapper, and restarts. Untracked UI settings survive the merge.
Disabled secondary instances remain available for later configuration without
changing the Codex or Claude Code harnesses.

T3 starts Pi in RPC mode with its normal user configuration. Pi's provider
extensions discover models, including gateway-backed GPT, Claude, and Gemini.
Skills, native MCP servers, context files, and extensions remain Pi-owned. Do not
add T3's session MCP endpoint to the shared MCP registry: T3 injects its own
extension and short-lived session credentials.

The injected bridge adds delegation, durable child threads, thread and queue
controls, scheduling, worktree tools, and the T3 preview and device tools. Tool
availability still depends on the environment and caller permissions. Pi owns
model execution and native sessions. T3 owns remote UI, orchestration, and
recovery. A second harness is a manual alternative, not automatic failover.

### Background text generation

T3 disables extensions and tools in its temporary Pi processes for titles,
branch names, and source-control text. Extension-defined providers such as
`cliproxy` are therefore unavailable to these helpers. Select a Pi built-in
provider with credentials already present in Pi's home. This does not change
the models available in coding threads.

### Permissions and extensions

T3's injected permission hook asks through Pi's extension UI. Auto-accept edits
recognizes `edit` and `write`, not the custom `apply_patch` tool. That tool still
requires confirmation unless the thread has full access. Codemode and custom
tools also require confirmation. These hooks are not an OS sandbox.

Extension dialogs are forwarded to the composer. Terminal widgets, custom TUI
components, and decoration do not have equivalent remote UI. Project-local
extensions and skills remain subject to Pi's project-trust rules.

## Check and maintain the service

```sh
uv run --script tools/t3/t3ctl.py status
uv run --script tools/t3/t3ctl.py doctor
uv run --script tools/t3/t3ctl.py restart
uv run --script tools/t3/t3ctl.py auto-update
uv run --script tools/t3/tests/test_t3ctl.py -v
```

On Linux, check `systemctl --user status t3code.service` and
`journalctl --user -u t3code.service -n 50`. Lingering keeps it running after
logout. On macOS, the service uses launchd and requires a logged-in, awake Mac.

For a floating release channel, `auto-update` postpones while the V2 database
contains preparing, starting, or running turns. An unreadable database aborts
the update. The guard does not guarantee background tools or terminals are idle.
The model-refresh timer only changes Claude models when its instance is enabled.
Pi discovers its own catalog and does not need that timer.

### Automatic updates

Sync installs the maintenance schedules described in
[User services](sync/sync.md#user-services). Release pinning is enforced by
`auto-update`, so the installed timer cannot move a pinned service.

### Switch from nightly to stable

First check that stable contains V2 and is not older than the pinned nightly.
Change `channel` in the deployment file, then run:

```sh
uv run --script tools/t3/t3ctl.py update
uv run --script tools/t3/t3ctl.py status
```

`update` reconciles the pinned runtime and service launcher, then reapplies
settings. Do not force a downgrade to V1. V2 uses `userdata/statev2.sqlite`;
V1 uses `userdata/state.sqlite`. The first V2 start copies V1 history once,
and later conversations do not sync between those databases.

## Ownership and upstream source

Keep runtime state, databases, secrets, pairing links, and service units untracked.
T3 owns `~/.t3/`. The repository owns only `tools/t3/` declarations and operations.
Validate settings against upstream `packages/contracts/src/settings.ts`:
invalid settings can cause the server to use defaults.

Read the vendored `github.com/pingdotgg/t3code` source for CLI behavior and
provider integration. Start with `docs/user/background-service.md`,
`docs/user/providers-pi.md`, `apps/server/src/orchestration-v2/Adapters/PiAdapterV2.ts`,
`piT3McpInjection.ts`, `piT3McpExtensionSource.ts`, and
`apps/server/src/textGeneration/PiTextGeneration.ts`.
