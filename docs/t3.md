# T3 Code server

T3 Code is a WebSocket server that hosts agent sessions for web, desktop, and mobile clients. It runs as a user service on the host named by `tools/t3/deployment.json` — systemd on Linux, launchd on macOS (the T3 installer picks).

This repository tracks the deployment declaration and desired configuration only. The service unit, `~/.t3/` runtime state (database, secrets, tokens, pinned versions), and Tailscale state are generated or live data and stay untracked.

## Prerequisites

`t3ctl.py` is stdlib-only Python. The host needs a user service manager (`systemctl --user` on Linux, `launchctl` on macOS), a JavaScript package runner (`npx` or `bunx`), and `tailscale` when tailnet exposure is enabled. Prefer node-backed runners for `install`/`update`: the generated unit inherits the invoking interpreter as its service runtime.

## Operate

All operations go through `tools/t3/t3ctl.py`, which reads `deployment.json` for the declared host and channel, and refuses to mutate on any other host:

| Command | What it does |
| --- | --- |
| `python3 tools/t3/t3ctl.py install` | Bootstrap the service on the declared host, apply desired settings, reconcile the model-sync scheduler, report next steps |
| `... t3ctl.py status` | Declared vs. live state: host match, unit, version, port, endpoint probe, exposures |
| `... t3ctl.py doctor` | `status` plus unit file, service state, and recent logs |
| `... t3ctl.py restart` | Restart and wait for the endpoint to answer |
| `... t3ctl.py update` | Install, update, or repair the service on the declared channel; reconciles the model-sync scheduler |
| `... t3ctl.py apply-settings` | Merge `server-settings.json` into live settings while stopped, then restart; also refreshes the Codex driver's `customModels` from the live CLIProxyAPI catalog so the picker tracks the gateway |
| `... t3ctl.py sync-models` | Refresh only `customModels` in live settings while running — the server watches `settings.json`, so the picker repopulates without a restart. Single-segment OAuth-pool ids are written first as `{slug, name}` entries whose display name carries the gateway owner (e.g. `gpt-6-astra (openai)`); multi-segment ids stay bare slugs. The web picker renders at most 32 custom models per instance in settings order, so OAuth-pool ids are emitted first; the full list still lands in settings and remains visible on mobile, which reads the uncapped server snapshot. Also repoints the OpenCode driver's `binaryPath` at the resolved npm-cache binary — the `~/.local/bin` sync wrapper adds ~3s per spawn and overruns T3's 4s version probe. An hourly scheduler runs this automatically: `t3-models-sync.timer` (systemd) on Linux, `dev.agents.t3-models-sync` (launchd agent) on macOS — both reconciled by `install`/`update` |
| `... t3ctl.py pair` | Mint a tailnet pairing link; also reconciles `tailscale serve` to the live port |
| `... t3ctl.py connect …` | T3 Connect management (`login`, `link`, `publish`, `status`, `unlink`) |
| `... t3ctl.py logs [-n N]` | Recent service journal and boot log |

First-time Connect setup on a new host: `connect login` (interactive browser auth), `connect link`, `restart`. With `exposure.publishAgentActivity`, also `connect publish` + `restart`.

## Deploy on a new host

1. Update `server.hostname` in `tools/t3/deployment.json` and commit.
2. On the new host: `python3 tools/t3/t3ctl.py install`, then the Connect steps above if enabled.
3. On the old host: `t3 service uninstall` and `t3 connect unlink` via `t3ctl.py connect …`.
4. Re-pair clients; Connect environments reappear through the account link.

## Deployment file

`tools/t3/deployment.json` fields:

| Field | Constraint | Meaning |
| --- | --- | --- |
| `server.hostname` | Local OS hostname | Host that runs the T3 Code service |
| `channel` | npm dist-tag | Release channel for install/update commands |
| `exposure.tailscaleServe` | Boolean | Server is proxied by `tailscale serve` on the tailnet |
| `exposure.connect` | Boolean | Environment is linked to T3 Connect |
| `exposure.publishAgentActivity` | Boolean | Server pushes agent activity to linked mobile clients |

## Settings file

`tools/t3/server-settings.json` is merged into `~/.t3/userdata/settings.json` by `apply-settings` (or `install`). Keep only non-secret, host-independent values; `~` expands to the server user's home. Sensitive or per-client changes belong in the client UI.

The tracked settings assume an always-on host driven remotely: the background-activity profile uses the performance cadence with lock-pausing off, so a locked desktop session never stalls background work. On a battery-powered or locally used host, revisit that profile. Setting keys and defaults are defined in the vendored source under `packages/contracts/src/settings.ts` and `packages/shared/src/backgroundActivitySettings.ts`.
